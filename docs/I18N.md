# Translating Aster

Aster ships in **English** and **Russian**. The interface language follows the browser by default (Profile, Language lets
you choose "Auto", English or Русский). Adding another language is mostly a translation job: one JSON file and a few lines of code.

## How it works

The translation layer is small and has no dependencies (`src/i18n/`).

- **The English text is the key.** Code reads `t('Sign in')`. Untranslated text falls back to English, never to a technical key.
- Other languages are JSON dictionaries in `src/i18n/locales/<id>.json`, mapping the English text to the translation.
  They are loaded lazily, so English users never download them.
- **Placeholders** use braces: `t('Hello, {name}', { name })`. A translation must keep the same placeholders.
- **Plurals** use `tn(count, '{n} day', '{n} days')`. In a dictionary, a plural message is an **array of forms** in the order
  given by the language's `plural` list in `LOCALES` (English: `one, other`; Russian: `one, few, many, other`). `{n}` is filled in automatically.
- **Context** separates identical English words that translate differently: `t('Call', undefined, 'verb')` is stored under
  the key `verb\u0004Call` (a context, then the control character U+0004, then the text).
- **Module-level constants** cannot call `t()` at load time. Mark the text with `msg('...')` and translate where it is shown with `t(value)`,
  or use a getter (`get label() { return t('Work') }`).
- **JSX with markup inside a sentence** uses `tx('Connected · {model}', { model: <b>Claude</b> })` from `@/i18n/react`.
- Keys must be **string literals** (no template strings with `${...}`). That is what lets the checker find them all.

## Add a language

Say you add German (`de`).

1. Register it in `src/i18n/index.ts`:
   - add `'de'` to the `Locale` type,
   - add a row to `LOCALES`: `{ id: 'de', name: 'German', native: 'Deutsch', tag: 'de-DE', plural: ['one', 'other'] }`
     (`plural` lists the CLDR plural categories your language uses, in the order of your dictionary arrays),
   - add a loader to `loaders`: `de: () => import('./locales/de.json').then(m => m.default as Dictionary)`.
2. Create `src/i18n/locales/de.json`. The quickest start is to copy `ru.json` and replace the values (keep the keys).
   `npm run i18n:check` lists every message that is still missing or has mismatched placeholders:
   ```bash
   npm run i18n:check            # fails on missing or malformed translations
   npm run i18n:check -- --strict # also fails on unused translations
   ```
3. Run the app (`npm run dev`), switch the language in Profile, and click through the screens. Long words may need a look on a phone.
4. Optional but recommended: add a demo pack (`src/data/demo/`) so the demo network reads naturally. Without one, the English demo is used.

That is enough for the whole interface. What follows is about the assistant.

## The on-device assistant (Astra) and other languages

- **Understanding input** is a union of languages: the on-device engine (`src/ai/local/`) recognizes dates, relations, cities,
  commitments and so on in English and Russian at the same time, whatever the interface language is. **Output** (what Astra writes)
  follows the interface language. To teach it a new input language, extend the word lists and patterns in `src/ai/local/text.ts`,
  `parse.ts`, `src/data/dates.ts`, `src/data/family.ts` and `src/voice/`, and add tests next to `tests/ai/*.en.test.ts`.
- **Message drafts** without a model have templates per language in `src/ai/local/drafts.ts` and `drafts.en.ts`.
  Other languages fall back to English templates.
- **With a cloud model**, Astra's system prompts exist in English and Russian (`src/ai/prompts.en.ts`, `prompts.ru.ts`).
  For any other language the English prompts are used with a line asking the model to answer in that language, so a new
  translation works with a cloud model out of the box. Write a dedicated prompt file for the best results.
- Voice input uses the language tag of the locale (`tag` in `LOCALES`) for the browser's speech recognition.

## Style guide for translators

- Keep the tone of the original: friendly, short, no jargon, no exclamation marks unless the English has them.
- Do not translate product names (Aster, Astra, Orbita, TickTick, Claude, Supabase).
- Prefer neutral wording that does not depend on the user's gender, where your language allows it.
- Keep placeholders and punctuation such as `…` and `·` where the English has them; keep the length similar, since the UI is a phone screen.
- Run `npm run i18n:check` before opening a pull request.
