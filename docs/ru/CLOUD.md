# Облако: как устроена синхронизация

[English](../CLOUD.md)

Aster остаётся **локально-первым**: интерфейс всегда читает и пишет в IndexedDB (Dexie), поэтому всё работает без интернета и мгновенно. Облако (Supabase) — копия, которая догоняет в фоне и связывает устройства одного аккаунта. Облако необязательно: если собрать приложение без `VITE_SUPABASE_URL` и `VITE_SUPABASE_KEY`, всех связанных с ним разделов в интерфейсе не будет.

## Схема

```
Dexie (устройство) ──hook──▶ outbox ──push──▶ sync_push() ──▶ records (Postgres, RLS)
        ▲                                                         │
        └────────── applyRemote ◀── pull (seq > курсор) ◀─────────┘
                                         ▲
                                  Realtime-пинг, фокус, сеть, таймер
```

- **Таблица `records`**: одна строка на любую запись приложения (`tbl`, `id`, `data jsonb`, `deleted`, `client_ts`, `seq`). Читать можно только свои строки (RLS). Писать напрямую нельзя — только функцией `sync_push`, которая сама подставляет владельца, проверяет формат и вырезает `settings.ai` (ключи Астры никогда не попадают в облако).
- **Очередь `outbox`** в Dexie: хуки на создание, правку и удаление кладут туда ключ строки. Удаление — это «надгробие» (`deleted = true`), чтобы оно дошло до других устройств.
- **Конфликты**: побеждает строка с большим `client_ts` (время правки на устройстве, монотонное). Это правило одинаково на сервере (`sync_push`) и на клиенте (`applyRemote`): своя несинхронизированная правка новее — облако её не затирает; облачная версия новее — заменяет локальную очередь. Предположение: часы устройств идут примерно верно.
- **Курсор** `seq` — возрастающий номер принятой правки. Клиент отступает назад на `PULL_OVERLAP`, чтобы не пропустить транзакции, зафиксированные позже. Применение идемпотентно (сравнивается содержимое), поэтому повторное чтение безвредно.
- **Защита от «ядовитой» записи**: если сервер насовсем отклоняет запись (слишком большая, неверный формат), пачка делится пополам, виновник откладывается (счётчик в экране «Облако»), остальное уходит. Сбой сети так не обрабатывается: там всё остаётся в очереди.
- **Неверные часы**: сервер не принимает метку правки позже своего времени больше чем на минуту, поэтому устройство с часами «из будущего» не выигрывает все конфликты навсегда.
- **Демо-данные** в аккаунт не попадают: при первом входе они удаляются с устройства.
- **Только на устройстве**: `settings.ai` (ключи и режим Астры), `lastBackupAt`, `backupSnoozeUntil`, а также кэш и учёт расходов ИИ. Правка этих полей в облако даже не ставится в очередь.

## Жизненный цикл

1. **Вход** — почта и пароль (`signInWithPassword`). Сессия хранится в `localStorage` и обновляется сама.
2. **Первое подключение**: если на устройстве уже были данные, они ставятся в очередь с метками «последняя правка» и сливаются с облаком (ничего не теряется, у более свежей версии приоритет).
3. **Другой аккаунт на том же устройстве**: локальные данные прежнего аккаунта удаляются (не отправляясь), чтобы не смешивать людей.
4. **Выход**: сначала досылается очередь; если досылать нечем (нет сети), нужно подтвердить. Затем данные убираются с устройства — в облаке они остаются.
5. **Синхронизация** запускается: через ~1,2 с после правки, при сигнале Realtime, при возврате в приложение, при появлении сети и раз в минуту. Одновременно идёт не больше одной; при ошибках — повтор с нарастающей паузой (3 с … 5 мин).

## Файлы

| Файл | Роль |
| --- | --- |
| `src/cloud/engine.ts` | очередь, отправка, получение, слияние (не знает про сеть) |
| `src/cloud/controller.ts` | запуск/остановка, таймеры, повторы, смена аккаунта |
| `src/cloud/cloud.ts` | вход, выход, ссылки из писем, удаление аккаунта |
| `src/cloud/remote.ts` | запросы к Supabase |
| `src/cloud/boot.ts` | лёгкая точка входа: включает хуки, остальное грузит лениво |
| `src/sheets/CloudSheet.tsx` | экран «Облако» |
| `supabase/migrations/` | схема, политики и функции |

## Свой проект Supabase

1. Создай проект и выполни `supabase/migrations/*.sql`.
2. Задай при сборке `VITE_SUPABASE_URL` и `VITE_SUPABASE_KEY` (publishable-ключ; см. `.env.example`).
3. В Authentication → URL Configuration укажи **Site URL** — адрес, где опубликовано приложение (на него ведут ссылки из писем). По желанию включи защиту от утёкших паролей и подключи свой SMTP: встроенная отправка писем сильно ограничена по числу писем в час.

## Проверки

- `npm test` — движок и контроллер на «серверах» в памяти с теми же правилами, что в SQL; случайные операции на трёх устройствах должны сойтись.
- `ASTER_E2E_URL=… ASTER_E2E_KEY=… ASTER_E2E_USER1=почта:пароль ASTER_E2E_USER2=почта:пароль npx vitest run tests/e2e/cloud` — живой прогон на настоящем Supabase (два устройства, Realtime, изоляция пользователей, запрет без входа, 300 записей). Нужны два тестовых пользователя; без переменных тесты пропускаются.
